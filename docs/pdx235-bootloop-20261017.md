# pdx235 LineageOS 24 microG boot failure, October 17

The owner installed the published October 16 rootless OTA through Custota.
Authorized ADB observed LineageOS 24.0-20261016, SDK 37, slot A, locked
bootloader, yellow verified boot, and enforcing verity. Android never reached
boot completion. Repeated system_server crashes report:

```
IllegalStateException: Signature|privileged permissions not in privileged permission allowlist: {com.google.android.gms (/product/priv-app/GmsCore): android.permission.DUMP}
```

The installed product permission XML contains neither a grant nor a denial for
DUMP. The failing path is AppIdPermissionPolicy.onSystemReady. This explains
the observed Android service restart loop; it does not establish bootloader
retry counters or snapshot merge state, which remain unavailable to ADB shell.

Helper abdede21c1b048e11700ec2789d0fb96ace0b0e4 explicitly denies DUMP in the
installed GmsCore product policy. This accounts for the request without granting
system-service diagnostic access. The regression checks the XML passed to the
product filesystem installer, failed on the prior helper, and passes with the
repair. All 282 helper unit tests passed (5 skipped).

The consumer pin and both compatibility manifests use that exact repair.
Existing APK locks, signing identities, privileged-permission enforcement and
verified boot remain unchanged. Private raw device logs are kept locally.

Prepare a repository-signed rootless build-only candidate and install through
recovery while preserving userdata. No downgrade, wipe, slot switch, bootloader
unlock, enforcement bypass, or public release is part of this repair preparation.
The repository-signed rootless repair from build
[39031144913](https://github.com/0cwa/ModOS/actions/runs/39031144913) was
downloaded and independently signature-verified against the installed OTA
certificate and previously recorded AVB public key. Its SHA-256 is
`4ee1fbcb8594305ab518c48e1390a89551bff1fe8a177dfc7814b1576b10f223`.
The external-SD copy was checksum-verified, synced and unmounted before the
owner installed it. The owner then reported that the repair worked.

This establishes owner-reported successful rootless boot after this repair.
ADB was disconnected when checking that report, so a post-repair boot-property
capture, microG functional checks, and a subsequent OTA persistence cycle
remain unobserved. No physical Magisk acceptance is claimed.
