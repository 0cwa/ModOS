# pdx235 candidate boot failure, October 13

The rootless October 9 candidate exported by ModOS commit `b8b2a1e`
(run [38318273364](https://github.com/0cwa/ModOS/actions/runs/38318273364))
failed to start Android on the physical Xperia 10 V. Private ADB logs from
slot B identify the failure:

```text
SELinux: seapp_contexts: Duplicated entry
SELinux: user=_app
SELinux: name=com.chiller3.msd
SELinux: partition=vendor
SELinux: seapp_context_lookup_internal: No match for app with uid 1000
zygote64: JNI FatalError called: (system_server) ... selinux_android_setcontext ... failed
```

The boot reported `reboot,zycold-fatal`, a locked bootloader, yellow verified
boot, and enforcing verity. These observations identify an app-context parsing
failure; they do not establish complete care-map or snapshot acceptance.
The phone subsequently booted the previous July 24 installation on slot A;
ADB observed `sys.boot_completed=1`, and the owner unlocked Android. No agent
flashing, slot changes, data wipe, or verification changes were performed.

The candidate helper `cf613de0494374bef2face58fd2bb00cc0b1dca2` copied
Custota and MSD platform app-context rules into both vendor and ODM files in
compatible mode. Android loads both with vendor precedence and rejects their
duplicate selectors. The helper correction appends module app-label rules once
in `plat_seapp_contexts`. Binary and CIL policy patching remain enabled.

The focused regression now checks that module selectors appear once across the
context files and that vendor/ODM app-context files remain unchanged while CIL
patches still reach their partition roots. It failed on the original helper
and passes after the correction. The development helper pin includes this fix;
production pins and publication quarantine remain unchanged.

The original candidate must not be reinstalled. Cryptographic and filesystem
inspection of the original outputs did not catch this Android parser constraint.
A corrected repository-signed candidate requires fresh output verification,
physical first boot, and successful-slot/OTA persistence observations before
acceptance. The previous slot remains the recovery option; do not wipe userdata
or disable verity to work around this failure.

The first repaired-helper build, run `38389845277`, passed artifact checks but
selected the provider's latest source: LineageOS 24.0, October 12, SDK 37.
It was not installed. The development source is now fixed to the original
October 9 filename and digest in the official API; missing or changed fixtures
are rejected. Ordinary production provider selection remains unchanged.

The original-source repair from run
[38391680781](https://github.com/0cwa/ModOS/actions/runs/38391680781),
ModOS `8aabc81` with helper `b269609`, was copied to external SD, verified on
the phone, and manually installed by the owner. After the owner rebooted,
ADB confirmed slot B, LineageOS 23.2 October 9, SDK 36, and
`sys.boot_completed=1` with 18 minutes uptime. The bootloader remained locked,
verified boot yellow, and verity and SELinux enforcing. The captured current
logs contain no original duplicate-entry/system-server fatal sequence. The
owner reports normal use and working microG. This establishes the bootloop
repair; recovery success logs, privileged successful-slot/snapshot state, and
a subsequent OTA persistence cycle remain unobserved.

The build bundled locked microG Services `0.3.15.250932` and Companion
`0.3.15.40226`. The owner's microG F-Droid updates are active as updated system
apps, both `0.3.16.1`; bundled copies remain underneath. The active Services
version is `0.3.16.1.252432`. The current upstream release observed October 13
is [0.3.17.252432](https://github.com/microg/GmsCore/releases/tag/v0.3.17.252432).
Upstream identifies both 0.3.17 and 0.3.16.1 as containing security fixes, so
the older build lock warrants a separately verified refresh.

The unchecked Services Framework self-check corresponds to absent
`com.google.android.gsf` (GsfProxy); the current adapter installs only Services
and Companion. The [official installation guide](https://github.com/microg/GmsCore/wiki/Installation)
documents GsfProxy as optional, mainly for legacy C2DM messaging. Its absence
does not require another firmware installation. Android 15 and newer need
the documented ADB low-target-SDK installation option if the owner chooses
to install this legacy component. No optional package was installed during
the boot repair verification.

## microG refresh and merge preparation

At the owner's request, the integration now pins microG `v0.3.17.252432`
(Services versionCode `252432034`, Companion `84022634`) and scheduled
LineageOS/pdx235 selects microG explicitly. Manual builds remain opt-in.
The consumer and both compatibility manifests pin the helper containing the
SELinux repair and new canonical lock. Renovate proposes future microG releases
without automerge; CI requires the release selector to match that immutable
helper lock. The helper lock refresh command and CI verify both real upstream
APKs against the unchanged official signer, SHA-256, size, package and version.

These source changes do not lift pdx235 publication quarantine, expand the
reviewed API-36 capability to Android 17, or establish OTA persistence. The
scheduled publishing job continues to fail closed while quarantine is active;
setting microG in its configuration does not authorize release publication.
